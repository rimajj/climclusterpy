Build an LMNN supervision signal
================================

LMNN clustering learns its metric from a class label for each cell.
:func:`~climclusterpy.compute_supervision` builds that signal from one of three sources and
returns a :class:`~climclusterpy.SupervisionResult`. You pass its ``.y`` (raw labels) or
``.encoded_y`` (contiguous integers, required by the torch trainers) to
:func:`~climclusterpy.cluster_matrix`.

.. code-block:: python

   sup = compute_supervision("koppen_geiger", features_df=monthly_climatology)
   sup.kind          # "koppen_geiger"
   sup.n_classes     # number of distinct classes
   sup.labels        # DataFrame: cell_id, latitude, longitude, cluster_label
   sup.labels_csv    # path to the labels CSV the generator wrote
   sup.y             # raw label values, shape (n_cells,)
   sup.encoded_y     # 0..n_classes-1, aligned; feed this to the per-cell LMNN modes

From climate: Köppen–Geiger
---------------------------

The package computes these classes from a monthly-climatology feature table and needs no
optional extras. ``features_df`` must carry ``cell_id``, ``latitude``, ``longitude`` and the 12 monthly columns
``tas_month_01``…``tas_month_12`` (°C) and ``pr_month_01``…``pr_month_12`` (mm/month).

.. code-block:: python

   from climclusterpy import compute_supervision

   sup = compute_supervision(
       "koppen_geiger",
       features_df=monthly_climatology,
       cold_threshold=0.0,       # C/D boundary (0.0 or -3.0)
       output_dir="out/",         # optional; a temp dir is used if omitted
   )

From model output: traits
-------------------------

This source clusters cells by simulated traits (VegC, height, SLA, ...). Pass the trait
columns as ``continuous_cols`` (plus an optional ``categorical_col`` such as a dominant
type), the parallel ``cell_ids``, ``latitudes`` and ``longitudes`` arrays, and ``n_clusters``.

.. code-block:: python

   sup = compute_supervision(
       "output",
       features_df=traits,
       cell_ids=traits["cell_id"].to_numpy(),
       latitudes=traits["latitude"].to_numpy(),
       longitudes=traits["longitude"].to_numpy(),
       continuous_cols=["vegc", "height", "sla"],
       categorical_col=None,          # e.g. "dominant_type"
       n_clusters=20,
       linkage_method="complete",     # the default, as in the published results
   )

From a shapefile: Ecoregions2017
--------------------------------

This source assigns each cell to a WWF Ecoregions2017 polygon by a spatial join. It needs
the ``[ecoregions]`` extra (GeoPandas) and a :class:`~climclusterpy.data.DataRegistry` that
describes the grid.

.. code-block:: python

   sup = compute_supervision(
       "ecoregions",
       registry=registry,
       ecoregions_shapefile="Ecoregions2017/Ecoregions2017.shp",
       ecoregion_id_column="ECO_ID",
   )

Ecoregions with only a few cells on your grid make poor training classes, because metric
learning draws several same-class neighbours for every cell. By default, the package
therefore merges every ecoregion with fewer than 10 cells into the nearest larger one. It
prefers a region of the same biome and realm within 1,500 km, then one of the same realm,
then any. Only a region with nothing large within 1,500 km (a remote island) is merged
further away. On the global half-degree land grid
this turns the 815 Ecoregions2017 regions present into 623 classes. ``ecoregion_min_cells=`` changes the minimum (``0`` keeps one class per ecoregion). The
package writes the merges, with the distance and the rule that chose each target, to
``ecoregion_merges_min<n>.csv`` beside the labels. The preference for biome and realm uses
the ``BIOME_NUM`` and ``REALM`` columns of the shapefile. With a shapefile that lacks them,
distance alone decides.
:func:`~climclusterpy.create_regions`, which uses the map itself as the regions, does not merge
unless you pass ``ecoregion_min_cells``. A cell centre on the border of two ecoregions, or
equally near two when no polygon covers it, gets the lower id, with a warning.

Without the extra, the call raises an ``ImportError`` that names ``[ecoregions]``. You can
get ``registry`` with ``DataRegistry.load("<output_dir>/original_grid.nc")`` from a finished
run, as ``clusters.registry`` from a :func:`~climclusterpy.create_clusters` result, or from
what defines your cells: ``DataRegistry.from_mask("land.nc")``,
``DataRegistry.from_cell_list("gridlist.csv")``, or for the LPJmL-FIT layout
``DataRegistry.from_soil_code("soil_code.nc")``.

Use the signal
--------------

.. code-block:: python

   from climclusterpy import cluster_matrix

   result = cluster_matrix(X, n_clusters=7, locally_weighted=True, supervision=sup, lmnn_mode="global")

The labels must be aligned row by row with the feature matrix ``X``. A length mismatch
raises a ``ValueError``.

In one call
-----------

With ``supervision=``, :func:`~climclusterpy.create_clusters` builds the signal itself:

.. code-block:: python

   from climclusterpy import create_clusters

   # climate zones computed from the climate input, no extra data
   create_clusters(input_dir, n_clusters=2000, locally_weighted=True, supervision="koppen_geiger")

   # ecoregion polygons: needs a shapefile and the [ecoregions] extra, no model output
   create_clusters(
       input_dir, n_clusters=2000, locally_weighted=True,
       supervision="ecoregions", ecoregions_shapefile="Ecoregions2017/Ecoregions2017.shp",
   )

   # model-output traits: need the model output in supervision_data
   create_clusters(
       input_dir, n_clusters=2000, locally_weighted=True,
       supervision="biomass", supervision_data="/data/model_output/trait_grids",
   )

If you omit it, ``supervision`` is the four traits ``("sla", "wooddens", "height", "biomass")`` when
``supervision_data`` is given and Köppen–Geiger otherwise.

Saved results are reused only for the same inputs
-------------------------------------------------

The trait dendrogram and the ecoregion assignment are slow to build, so the package saves
them in ``output_dir`` and reads them back on the next call. It reads them back only when
the inputs match the ones that produced them (the trait matrix and linkage; the grid,
shapefile and id column) and computes anything else afresh. ``force_recompute=True`` rebuilds
regardless. Before 0.3.0
the file name alone decided, so a second call with other inputs in the same folder silently got
the first call's labels.
