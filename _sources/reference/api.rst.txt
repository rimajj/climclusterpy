Public API: :mod:`climclusterpy`
================================

.. py:module:: climclusterpy

A few calls cover the whole workflow: reduce a grid (:func:`create_clusters`), run your
vegetation model on the small one, and rebuild the full grid
(:func:`reconstruct_original_grid`). You import everything on this page from the
package itself::

   from climclusterpy import create_clusters, reconstruct_original_grid

The functions that use heavy or optional dependencies (``torch`` for metric learning,
``geopandas`` for ecoregions, ``pyet`` for SPEI) import them when called, so
``import climclusterpy`` works on the core install.

.. currentmodule:: climclusterpy

Describing the input
--------------------

The package accepts any named climate and static fields and any land mask or cell list.
Pass them to :func:`create_clusters`, :func:`create_regions` or :func:`check_inputs`
directly as ``climate=``, ``static=``, ``land_mask=`` and ``grid=``, or build them first
as a :class:`GenericInputs` and pass that (see :doc:`../howto/inputs`). The LPJmL-FIT file
layout has its own preset, :class:`~climclusterpy.data.DataPaths`.

Other ways to build the reduced grid
------------------------------------

:func:`create_regions` uses a map you already have as the partition instead of
clustering. :func:`draw_cells` makes the random cell draw of ``cell_selection="random"``
and ``"distributed"`` on its own, without building a grid.
:func:`create_regions` returns the same result object as :func:`create_clusters`, so
:func:`reconstruct_original_grid` works on it unchanged; :func:`draw_cells` returns the
table that result carries as ``selected_cells``.

.. autofunction:: create_regions

.. autofunction:: draw_cells

Reusing a trained metric
------------------------

Every metric :func:`create_clusters` trains is saved to ``<output_dir>/learned_metric``.
:func:`load_metric` reads it back, or reads a ``model.pth`` from an earlier research run.
``create_clusters(learned_metric=...)`` and ``cluster_matrix(learned_metric=...)`` then
cluster under it without training again. On the published global metric, this reproduces
the deployed labels exactly, at every number of clusters.

The model's other inputs
------------------------

The reduced grid carries the fields it was clustered on. :func:`subset_inputs` brings every
other input that the model opens onto the reduced grid (NetCDF, or LPJmL
``.clm``/``.clm.json``/raw), with each cell holding its source cell's values. LPJmL binaries
are read by position, so the function matches their cells by coordinate in the full run's
grid file (:func:`cell_index_in_grid`). The package's cell order and that of LPJmL's global
grid files differ, and a positional join between them is silently wrong. :attr:`CreateClustersResult.slot_sources` lists, for every written cell, where it
sits and whose data it carries.

.. autofunction:: subset_inputs

:func:`~climclusterpy.io.cell_index_in_grid` and :func:`~climclusterpy.io.read_lpjml_grid`
are documented with the other file helpers on :doc:`toplevel`.

Writing the reduced grid yourself
---------------------------------

If you build the per-cluster timeseries yourself,
:func:`~climclusterpy.grid.build_reduced_grid` (also importable as
``climclusterpy.build_reduced_grid``) writes the model-ready grid with every cell at the
coordinates of the cell whose climate it carries. After
:func:`~climclusterpy.io.assert_uniform_axes` (``climclusterpy.assert_uniform_axes``) has
checked the grid, :func:`~climclusterpy.io.convert_netcdf_to_clm`
(``climclusterpy.convert_netcdf_to_clm``) turns it into LPJmL's ``.clm`` binaries. :doc:`grid`
documents all three functions and the related placement functions.

Building blocks
---------------

These functions run single steps: clustering a feature matrix that you built, or building a
label signal on its own. To reconstruct from mapping CSVs that you already have, call
:func:`reconstruct_original_grid` with ``registry=``, ``id_mapping_csv=`` and
``compact_map_csv=`` instead of ``clusters=``.
